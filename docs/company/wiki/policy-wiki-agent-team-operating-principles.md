# Політика: Принципи роботи команди wiki-агентів

> [!WARNING]
> Документ має статус `draft` і потребує підтвердження.

## Мета

Зафіксувати єдині принципи, за якими команда wiki-агентів перетворює живі кейси, питання та рішення Secret Shop на структуровану корпоративну Wiki.

Результат:
- команда працює за спільною моделлю;
- знання не залишаються тільки в чаті;
- repo та Outline не плутаються як джерела істини;
- кожен агент розуміє межі своєї ролі.

## Область застосування

Політика застосовується до:
- роботи команди wiki-агентів у Telegram-групі;
- аудиту, написання, рев’ю та публікації Wiki-документів;
- перетворення кейсів, інцидентів, рішень і повторюваних питань на Wiki-артефакти.

## Базові принципи

1. Telegram-група є первинним робочим середовищем для взаємодії команди.
2. Repo `/root/company-wiki` є канонічним джерелом істини.
3. Outline є шаром читання та публікації, але не замінює repo.
4. Живий кейс, інцидент або рішення повинні перевірятися на `wiki-impact`.
5. Перед створенням нового документа потрібно шукати related existing doc.
6. Якщо даних бракує, агент ставить `TODO`, а не вигадує правило.
7. Документи для внутрішньої Wiki пишуться українською мовою, коротко та операційно.

## Що дозволено

- ✅ Проводити аудит існуючої структури Wiki.
- ✅ Пропонувати нові документи, якщо existing doc не покриває процес або правило.
- ✅ Оновлювати existing doc, якщо цього достатньо для вирішення задачі.
- ✅ Виносити відкриті питання та TODO, якщо факт не підтверджений.
- ✅ Декомпозувати роботу на ролі: шеф-редактура, аналітика, копірайтинг, аудит, реліз.
- ✅ Публікувати в Outline тільки після появи канонічної зміни в repo.

## Що заборонено

- ❌ Вважати Outline канонічним джерелом знань.
- ❌ Створювати канонічний контент тільки в Outline без repo.
- ❌ Вигадувати бізнес-факти, ролі, строки або правила без підтвердження.
- ❌ Створювати новий документ, якщо достатньо оновити existing doc.
- ❌ Завершувати роботу на рівні ідеї без реального артефакту в Wiki.
- ❌ Публікувати зміни як офіційні, якщо документ ще не пройшов потрібне погодження.

## Робочий цикл команди

1. Отримати кейс, питання, проблему або рішення в Telegram.
2. Оцінити `wiki-impact`.
3. Знайти existing related doc.
4. Визначити дію:
   - update existing doc;
   - create new draft;
   - зафіксувати TODO або відкрите питання.
5. Підготувати зміну в repo.
6. Провести рев’ю.
7. Запустити `npm run validate` і `npm run build`.
8. За потреби опублікувати документ в Outline.

## Ролі команди

| Роль | Відповідальність |
|---|---|
| Шеф-редактор | Приймає задачу, визначає маршрут роботи, вирішує: update existing doc чи new draft, тримає єдину редакційну логіку Wiki. |
| Аналітик | Шукає прогалини, дублікати, related docs і потрібний контекст. |
| Копірайтер | Готує український draft-документ у правильному типі та структурі. |
| Аудитор | Перевіряє якість, логіку, узгодженість і відсутність дублювання. |
| Релізер | Запускає validate/build і супроводжує публікацію в Outline. |

## Наслідки за порушення

Порушення цієї політики призводить до:
- дублювання або розсинхронізації знань;
- появи неканонічних правил;
- втрати трасованості рішень;
- публікації неперевірених або непогоджених матеріалів.

Результат: такі зміни мають бути переглянуті, виправлені або відкликані.

## Відповідальний за виконання

| Роль | Відповідальність |
|---|---|
| Founders / відповідальний за Wiki-контур | Підтверджує модель роботи та правила публікації. |
| Команда wiki-агентів | Дотримується цієї політики під час щоденної роботи. |
